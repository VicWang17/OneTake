# 我用不到 80 块钱，写了一个 AI 视频工厂

> OneTake 开发复盘：一条选题 8 分钟变成 60 秒视频，单条成本 ¥7.29，重跑不要钱。
> 这不是一篇"教你接 API"的文章，而是讲清楚：**把大模型能力变成一个可靠的生产系统，中间隔着多少工程问题。**

## 一、做了什么

OneTake 是一个端到端的 AI 视频创作工作台。给它一句选题（比如"为什么天空是蓝色的"），它自动完成：大纲 → 脚本 → 分镜表 → 分镜图 → 图生视频 → 配音 → 字幕 → BGM → 成片。中间任何一步可以人工查看、修改、重生成。

先放真实数据（系统内全部可审计）：

- 单条 60 秒成片（8-10 镜头）：**¥7.29**，约 8 分钟
- 同一个项目重跑一次：**¥0.00**，12 秒（幂等缓存全命中）
- 视频模型选型实测：fast 档比标准档**便宜 69%、快 27%**
- 全项目（含所有调试、试错、演练）：**不到 ¥80**

技术栈：Python / LangGraph / FastAPI / SQLite / FFmpeg，模型全部外购 API（DeepSeek、火山 Seedream/Seedance、百炼 Qwen-VL、edge-tts），单机无 GPU。

## 二、先图后视频：成本结构的第一性原理

视频生成是整条管线里唯一显著付费的环节（实测占单条成本 77.8%），而它恰恰是最不可控的——画面崩了、角色变了、动作乱了，都得重来。

所以整个架构的核心决策是：**把所有"决策"前置到便宜的阶段**。

```
选题 → 大纲 → 分镜表 → 分镜图（¥0.20/张，人工确认）→ 视频（¥0.71/5s，只负责"动起来"）
```

构图、风格、角色在图片阶段定死并确认；视频生成时把确认过的分镜图作为首帧（base64 内联传给 API），模型只负责让画面动起来。这样昂贵的视频调用几乎不做"探索性消耗"——它不是在"生成画面"，是在"执行已确认的画面"。

这个决策的韧性后来两次救场：视频模型未开通时，系统用分镜图 Ken Burns 推近填充照样出片（全图卡模式）；调试期的 9 次重跑，只花了 2 张图的钱。

## 三、按 token 计费时代：选档是选单价，不是选用量

接入 Seedance 2.0 时实测出一个关键事实：同一分辨率和时长下，**标准/fast/mini 三个档位的 token 数完全相同**（5s 480p 都是 50638 tokens）——token 数是"分辨率 × 时长 × 帧率"的函数，与模型档位无关。

这意味着成本优化的空间只有两个方向：

1. **选每 token 单价低的档**：fast 14 元/M tokens vs 标准 46 元/M，同样一条 5s 视频，¥0.71 vs ¥2.31
2. **减少无效生成**：先图后视频、幂等缓存

不存在"省 token"这条路——除非你降分辨率。计费也别按官方"每秒参考价"估算，要按厂商返回的 usage 反算，成本报表的每一分钱才都可审计。

## 四、幂等缓存：指纹的原料必须只含语义

调试期管线要反复重跑，没有缓存就是烧钱机。设计是内容寻址缓存：

```
idem_key = sha256(任务类型 + 模型 + 档位 + 语义参数)
```

收敛在网关统一入口，命中直接返回产物、记一行 `cache_hit`（成本 0）。效果：同项目重跑 12 秒、零成本。

但上线第一天就翻车了。服务化改造后，HTTP 层的 pydantic 模型给请求自动填了默认值（`size=1280x720`）、还把路由字段 `tier` 并进了请求体——**同样的内容，走 HTTP 和直连算出两个不同的指纹**，旧缓存全部静默失效，重新生成、覆盖文件、参考图内容变化、连锁失效……一次 key 污染引发一场雪崩。

修复立了一条铁律：**指纹原料只含语义参数，传输层的任何归一化（默认值填充、路由字段）必须先剥离**。

还有两个配套教训：

- 缓存命中和真实调用是**两条返回路径**，字段契约必须一致（真实路径有 `latency_ms`，缓存路径没有，调用方直接 KeyError）
- 命中记录必须带归属维度（project_id），否则"功能正确但统计错误"——首批 24 次命中永远丢失了命中率归属

## 五、确认式自动化：人工节点是状态，不是阻塞 IO

"人在关键环节确认"听起来简单，实现上有个分水岭：

- **朴素做法**：流程函数里 `input()` 等用户输入。问题：进程必须活着等——关终端、合盖休眠，"等待"这个位置就蒸发了
- **正确做法**：把确认建模为可持久化的**状态**。LangGraph 的 interrupt + SQLite checkpointer：图执行到确认点暂停、状态落盘、进程可以退出，明天回来从那个问题前继续

人的响应时间是小时级，进程的合理生命周期是秒级——**两者解耦，各自安好**。

配套的恢复语义也验证过：kill -9 进程后重启，从最后完成的节点继续；节点内已完成的付费调用被缓存接住，零重复扣费。**checkpointer 管"流程位置"，缓存管"钱不重花"，两层正交。**

## 六、EDL 与渲染分离：剪辑层的 bug 修复永远零成本

剪辑引擎的核心抽象是 EDL（Edit Decision List，剪辑决策表）——一份描述最终时间轴的 JSON：镜头序列、入出点、字幕段、BGM 轨、音量包络。管线只产出 EDL，渲染器负责翻译成 FFmpeg 命令。

这个分离在实战中的回报：修过三次剪辑层 bug（混音增益、音轨选流、闪避参数），每次修复都是改代码 + 重渲染，**零 API 成本、零素材重生成**。如果渲染和生成耦合，每个剪辑 bug 都要再花 ¥7 重出素材。

另一个具体坑值得单独说：视频按 5 秒粒度生成，台词是 4–8 秒的任意值。对齐规则是**时间轴以音频实测时长为准**，视频短了就 `setpts` 慢放补齐（插画片 0.75 倍速无感）——零成本时域变换，比为两三秒缺口重新生成 10 秒素材（价格翻倍）聪明得多。

## 七、两个"软"系统：Skills 与记忆

**Skill 技能库**：把"一种视频该怎么做"（叙事结构、语言/画面风格、BGM 选择、匹配规则）声明为 YAML 包，LLM 按选题自动选择。关键设计是 Skill 只替换风格数据的**来源**（YAML vs LLM 临场发挥），不改变数据**形状**——下游管线零改动，新 Skill 上线对系统透明。

**长期记忆**：Mem0 式轻量实现。两类记忆（画像偏好/经验教训），LLM 负责语义归并（新记忆进来先判断：add / merge / contradict），置信度证据驱动调整（新条 0.5、归并 +0.15、矛盾 -0.2、低于 0.3 软删除）。验证记忆生效要看**因果性**：手动加入"标题必须带数字"这条记忆后，下一次产出的大纲标题变成了《……？3 个真相》——加了 X 输入，输出就出现 X，才算数。

## 八、踩坑精选（真正的学费）

**ffmpeg 的坑三连：**

1. homebrew 的默认 ffmpeg 是精简构建，**没有 libass**——`subtitles` 滤镜不存在，字幕烧录直接报 unknown filter。解决：装 `ffmpeg-full`，项目用独立路径，互不干扰
2. **默认选流规则**：`-i 视频 -i 配音` 不写 `-map` 时，ffmpeg 按"声道多者胜"自动选音轨——结果选了 Seedance 视频内嵌的 AI 音轨，我们的 TTS 配音被静默丢弃。`多路输入，必写 -map`
3. **AAC priming**：AAC 编码器在流开头塞 1024 样本的前导延迟（≈23ms），重封装丢了 edit list 后波形偏移。我用零滞后相关性验证"人声在不在"时全部误报——**验证音频内容一致性要用带滞后补偿的波形相关性，响度只是标量，会撒谎**

**评估器本身需要被评估**：VLM 质检上线首跑 8/8 全过，我没有急着高兴——喂了一个刻意错配的样本（彩虹视频配"橘猫做红烧肉"的描述），评分器果断判了 semantic=1。这才有理由相信前面的全 5 分是真实质量，不是"老好人评分器"。

**熔断的实战**：日预算熔断在真实运行中触发过一次——付费调用被拦在门外、重试如实失败、其他镜头无连坐、提额后续跑增量成本精确到 ¥0.71。护栏类机制必须在真实失败里演练一次，设计文档不算数。

## 九、不足与后续

- 角色一致性目前是"文本锚点 + 参考图链"的零成本组合，管得住"长什么样"，管不住"出不出场"（已经踩过：人物剪影被注入到不该出现的场景镜头，修复为条件注入）。再上一步是 IP-Adapter 类方案
- 调度器是 SQLite 单机队列，并发 ≤5 的当前规模够用；到 50+ 并发或多机要迁 Redis——选型是刻意的，迁移路径也清楚
- 质检的重生成回路还没有被真实低分触发过（首次全过）——逻辑已备，等实战

## 结语

这个项目最大的收获不是"接了多少 API"，而是一个反复被验证的判断：**大模型能力的门槛在降低，但把它变成可靠系统的工程门槛没有变**——幂等、熔断、降级、可观测、数据驱动，这些"老"工程问题在 AI 系统里一个不少，只是因为每一次调用都标价，答错的代价比以前更直观。
